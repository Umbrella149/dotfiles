# 05 · 怎么让 AI 帮你改配置

你说不会 Lua。这份文档教你怎么提需求，让 AI 改出来的东西**你依然能看懂、能维护**。

---

## 核心原则：先给坐标，再说需求

AI 最容易犯的错是「把改动塞到它觉得方便的地方」，结果配置结构越来越乱。
所以**你要指定改哪个文件**。

对照表 —— 想改什么，该动哪个文件：

| 你想改的东西 | 告诉 AI 改这个文件 |
|---|---|
| 行号、缩进、搜索、界面选项 | `lua/core/options.lua` |
| 快捷键（不涉及插件的） | `lua/core/keymaps.lua` |
| 「保存时自动做某事」这类行为 | `lua/core/autocmds.lua` |
| 报错警告的显示方式 | `lua/core/diagnostic.lua` |
| 底部状态栏 | `lua/core/statusline.lua` |
| 某个语言单独的缩进等 | `after/ftplugin/<语言>.lua` |
| 加/删插件 | `lua/plugins/deferred.lua` |
| 某个插件的设置或它的键位 | `lua/plugins/<插件名>.lua` |
| 加一门语言的 LSP | 新建 `lsp/<server名>.lua` + 改 `lua/lsp/init.lua` |
| LSP 的通用键位、补全行为 | `lua/lsp/init.lua` |
| 格式化工具 | `lua/plugins/conform.lua` |

不确定改哪个？直接说：**「先告诉我这个功能在哪个文件里，不要改」**。

---

## 提需求的模板

```
在 <文件名> 里，我想要 <具体行为>。
按现有风格写，加中文注释说明为什么这么写。
```

「按现有风格写」很重要 —— 配置里的注释密度、命名方式、`local map = vim.keymap.set`
这种写法都是统一的，AI 会跟着模仿。

## 好例子 vs 坏例子

### 例 1：改键位

❌ **「帮我加个保存的快捷键」**
→ AI 不知道加在哪、什么键、要不要覆盖已有的。

✅ **「在 `lua/core/keymaps.lua` 里加：normal 模式按 `<leader>fs` 保存当前文件。
按现有风格写，带 desc 和中文注释。」**

### 例 2：装插件

❌ **「我想要自动补全括号」**
→ AI 可能装 mini.pairs、可能装 nvim-autopairs、可能自己写一堆 autocmd。

✅ **「装 `windwp/nvim-autopairs` 这个插件。按照 `docs/02-插件层.md` 里
『加一个插件』的四步来做：加到 `deferred.lua` 的清单、新建 `lua/plugins/autopairs.lua`
写配置和中文注释、在 `deferred.lua` 底部 require、然后告诉我重启后怎么验证它生效了。」**

（把文档路径给 AI，它就会照着你的结构走，不会自创一套。）

### 例 3：不确定要什么

❌ **「我觉得搜索不太好用，帮我改改」**

✅ **「我现在用 `<leader>sg` 全局搜索，但我想在搜索时排除 `build/` 目录。
这是 fzf-lua 的配置，在 `lua/plugins/fzf.lua`。先告诉我有几种做法和各自的取舍，
我选完你再改。」**

### 例 4：出问题了

❌ **「配置报错了」**

✅ **「打开 `.cpp` 文件时状态栏没显示 clangd。我跑了 `:checkhealth lsp`，
输出是：<粘贴输出>。帮我排查。」**

排查类问题的通用做法：**先跑诊断命令，把输出粘给 AI**。
常用诊断命令在 [00-总览.md](00-总览.md#日常维护命令)。

## 让 AI 教你，而不只是帮你改

你说很多功能对你「像魔法」。破解魔法的提问方式：

```
「<leader>ff 这个键是哪来的？是 Neovim 自带还是插件？在哪个文件定义的？」

「我按 K 会弹出文档窗口，这个功能是谁提供的？」

「lua/plugins/fzf.lua 第 20 行的 register_ui_select() 是干什么的？
不加会怎样？」

「解释一下 lua/lsp/init.lua 里的 LspAttach 是什么，为什么键位要写在里面
而不是全局？」
```

也可以自己查（不用问 AI）：

```vim
:verbose map <leader>ff     " 这个键是哪个文件第几行定义的
:help vim.lsp.completion    " 查原生 API 文档
:checkhealth                " 全面体检
```

## 几条硬性要求，建议每次都加上

在需求后面附上这些，能避免配置腐化：

```
1. 不要为了这个功能装新插件，除非原生真的做不到 —— 如果要装，先告诉我原生方案是什么，
   以及为什么不够用。
2. 改动放在对应的文件里，不要新建抽象层（utils/、helpers/ 之类）。
3. 加中文注释，说明「为什么」而不只是「是什么」。
4. 改完告诉我：改了哪些文件、每个文件改了什么、怎么验证生效了。
5. 如果这个改动和现有键位/设置冲突，先告诉我，别自己决定。
```

---

## 最有用的一句话

> **「先解释，别动手。」**

尤其是当你还不确定自己想要什么的时候。AI 会倾向于立刻写代码，
而你更需要的往往是先搞清楚「这件事有几种做法」。

## 配置改坏了怎么办

**先做好这一步**（还没做的话现在做）：

```bash
cd ~/dotfiles
git init
git add -A
git commit -m "nvim 配置初始版本"
```

之后每次改动前后：

```bash
cd ~/dotfiles
git diff              # 看改了什么
git checkout -- .     # 全部回退到上次提交
git add -A && git commit -m "加了 xxx"   # 满意了就提交
```

**紧急情况：配置报错到打不开 nvim**

```bash
nvim --clean          # 完全不加载任何配置启动，用它来修配置文件
```

或者临时禁用整个配置：

```bash
mv ~/.config/nvim ~/.config/nvim.bak
```

## 一个完整的对话示例

> **你**：我想在写 C++ 时按一个键就编译并运行当前文件。先别动手，
> 告诉我有几种做法，以及分别会改哪些文件。
>
> **AI**：（给出三种方案：a) 用原生 `:make` + `makeprg`；b) 写个 Lua 函数调
> `vim.system`；c) 装 overseer.nvim 之类的任务插件。说明各自改哪些文件、取舍是什么。）
>
> **你**：用方案 a，原生的就好。改 `after/ftplugin/cpp.lua`，键位设成 `<leader>cc`。
> 加中文注释说明 makeprg 是什么。
>
> **AI**：（改文件，说明改了什么、怎么验证。）
>
> **你**：`makeprg` 里的 `%` 和 `%<` 分别是什么意思？

这样下来，你不但拿到了功能，还搞懂了 `:make`、`makeprg`、`%` 这几个原生概念。
下次自己就能改了。
